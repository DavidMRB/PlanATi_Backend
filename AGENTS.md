# AGENTS.md

This file provides guidance to Codex (claude.ai/code) when working with code in this repository.

PlanATi backend: a FastAPI API for searching, rating and managing gastronomic establishments. Code, comments, API error messages and docs are written in Spanish — keep new user-facing strings in Spanish.

## Commands

```bash
pip install -r requirements-dev.txt     # runtime + pytest + aiosqlite
docker compose up -d                    # PostGIS 16 on host port 5433 (not 5432)
python -m scripts.backup_db create --tag pre-<revision>   # ALWAYS before applying a new migration locally
python -m alembic upgrade head          # apply migrations
uvicorn app.main:app --reload           # health check: GET /api/v1/health
pytest                                  # all tests
pytest tests/test_phone_verification.py::test_otp_flow_and_single_use   # single test
python -m scripts.seed_demo up|status|down   # demo data in Cúcuta (@demo.planati.test accounts only)
python -m scripts.run_reminders --once          # one reminders/complete/purge pass (cron alternative to the in-process loop)
python -m scripts.backup_db list|restore <file> [--target planati_restore]|prune
```

`DATABASE_URL` uses `postgresql+asyncpg://...`; the config default points at port 5432, so with the Compose database set `.env` to port 5433. Copy `.env.example` to `.env` for local setup.

Backups (`scripts/backup_db.py`) run `pg_dump`/`pg_restore` inside the `planati-postgres` container and write to `backups/` (git-ignored, contains personal data). Tagged backups are never pruned. To verify a dump without touching the main DB, restore it with `--target <scratch_db>` and drop that DB afterwards.

## Architecture

Layering is `app/api/routes/*` (HTTP, status codes) → `app/services/*` (business logic, takes an `AsyncSession` as first arg) → `app/models/*` (SQLAlchemy 2.x declarative, `app/db/base.py:Base`). Pydantic DTOs live in `app/schemas/`. Services signal domain errors with `ValueError` or custom exceptions (e.g. `PhoneVerificationError`) that routes translate into `HTTPException`. All routers are mounted under `settings.api_v1_prefix` (`/api/v1`) in `app/main.py`.

- **Async everywhere**: the app uses `create_async_engine` + `asyncpg`; the `get_db` dependency in `app/api/dependencies.py` yields an `AsyncSession`. Alembic, however, runs synchronously — `migrations/env.py` rewrites the URL from `+asyncpg` to `+psycopg`.
- **Migrations** are hand-numbered (`migrations/versions/000N_*.py`). New models must be imported in `app/models/__init__.py` so `Base.metadata` (used by Alembic and by tests' `create_all`) sees them.
- **Settings** come from `app/core/config.py` (`pydantic-settings`, reads `.env`, module-level `settings` singleton). With `APP_ENV=production`, `app/core/startup_checks.py:enforce_settings` (called in the `lifespan`) refuses to start on weak `SECRET_KEY`, non-https/localhost URLs, `SMS_PROVIDER=mock`, `planati:planati` DB credentials or R2 placeholders; `/docs` is off in production unless `ENABLE_API_DOCS=true`.
- **Time**: store and compare datetimes in UTC only (`DateTime(timezone=True)`); SQLite drops the offset, so normalize with `app/core/time.py:ensure_utc` before persisting/comparing and after reading. `APP_TIMEZONE` (America/Bogota, via `to_local`/`local_day_start`) is only for validating schedules, user-facing text and "start of day" for daily limits.
- **Pagination**: new list endpoints return `app/schemas/common.py:Page[T]` (`items`, `total`, `skip`, `limit`).

### Authentication and access control

- JWT (HS256, `sub` = user id, plus `iat` and a per-session `csrf` claim) created in `app/core/security.py`. `get_current_user` accepts the token from an `Authorization: Bearer` header **or** the `HttpOnly` cookie named by `settings.access_token_cookie_name`. Cookie attributes come only from `session_cookie_params()` (used by `set_auth_cookie`, `clear_auth_cookie` and the `oauth_state` cookie; `Secure` is forced in production). Routes that create a session call `start_session()` in `app/api/routes/auth.py` and return its `csrf_token`. The JWT never goes in JSON or URLs (see `GUIA_AUTENTICACION_COOKIE_HTTPONLY.md`).
- **CSRF** (`app/core/csrf.py`, global dependency `csrf_protect` in `app/main.py`): every POST/PUT/PATCH/DELETE must come from a trusted `Origin`/`Referer` (`CSRF_TRUSTED_ORIGINS`, default `CORS_ORIGINS` + `FRONTEND_URL`), and cookie-authenticated ones must send `X-CSRF-Token` equal to the session's `csrf` claim (`GET /auth/csrf` returns it). Bearer requests are exempt; login, registrations, Google exchange and logout are exempt from the token only (listed in `TOKEN_EXEMPT_PATHS`). Failures are 403 `{"detail", "code": "CSRF_FAILED"}`. Never make a GET route change state.
- Google OAuth (`app/integrations/google.py`): `/auth/google` sets a signed `oauth_state` cookie → `/auth/google/callback` verifies it, issues a short-lived one-time code (`OAuthLoginCode`, stored hashed) and redirects to `{FRONTEND_URL}/google-callback?code=...` → frontend calls `POST /auth/google/exchange` to get the session.
- Phone OTP (`app/services/phone_verification_service.py`): Colombian numbers normalized to `+57...`; codes stored hashed, single-use, with expiry/attempt/resend-cooldown limits from settings. SMS goes through a provider abstraction in `app/integrations/sms.py`; `SMS_PROVIDER=mock` only logs the code (it is never returned in HTTP responses). Tests swap the provider by monkeypatching `phone_verification_service.get_sms_provider`.
- User lifecycle: new users start with `status="PENDING_PHONE"`, `phone_verified=False`; verifying the OTP sets `ACTIVE`. A user with a verified phone cannot change it through `PATCH /users/me` (400). Changing it goes through `POST /users/me/phone/send-code` and `POST /users/me/phone/verify`, which leave the account `ACTIVE` with the old number until the new one is confirmed. Only the first-time setup (`/auth/phone/send-code`) puts the account in `PENDING_PHONE`. Use the dependencies `require_active_user` (verified + `ACTIVE`) for any route that creates/modifies establishments, reviews, etc., and `require_admin` (role `admin` + active) for admin routes.

- **Privacy (B8, Ley 1581)** in `app/services/privacy_service.py`: current legal versions come from `PRIVACY_POLICY_VERSION`/`TERMS_VERSION`; registrations require `accept_privacy_policy`, `accept_terms` and both versions (no minimum age, D10), and every acceptance inserts `consents` rows and copies the versions onto `users`. Every `require_*` dependency calls `ensure_consents` → 403 `{"detail", "code": "CONSENT_REQUIRED", "pending_consents"}`; `get_current_user` does not, so `/users/me`, `POST /users/me/consents`, export, delete and logout keep working. Test users from `create_user` are born with the current versions (pass `privacy_policy_version=None` to test the gate); registration payloads use `consent_fields()` from `conftest.py`. `DELETE /users/me` (role `user` only, password or a `DELETE_ACCOUNT`-purpose SMS code) hard-deletes reviews (recalculating ratings), plans, favorites and notifications but keeps the `users` row as an anonymized tombstone (`status="DELETED"`, rejected by `get_current_user` with 401) so the moderation log (details redacted), reports and consents (without IP/UA) keep pointing at a valid id. Any new user-owned table must be handled in `delete_account` and `export_user_data`.

### Notifications

In-app notifications (`app/models/notification.py`, `NotificationType`) are read by the frontend by polling `GET /notifications/unread-count`; `/notifications` routes use `get_current_user` (any role/status except `SUSPENDED`, so a `PENDING` restaurant sees its approval) and filter by the current user (foreign id → 404). Create them only with `app/services/notification_service.py:notify(...)` / `notify_admins(...)`, which add to the session **without committing**: call them inside the operation that triggers them, before its single `commit()`. Pass a `dedupe_key` when a notification must exist only once (e.g. reminders). Approving/rejecting an establishment notifies its owner.

### Administration and moderation

- **Suspension**: users and establishments can be `SUSPENDED` (distinct from `REJECTED`, which is only for `PENDING` requests). `get_current_user` raises `AccountSuspendedError` → 403 `{"detail", "code": "ACCOUNT_SUSPENDED", "reason"}` (so an issued cookie stops working at once); login and Google exchange do the same; `get_optional_current_user` treats a suspended account as anonymous. A suspended establishment gets `EstablishmentAccessError("SUSPENDED")` across the panel.
- `app/services/moderation_service.py` (log + review/reply/image/menu actions), `admin_service.py` (accounts, establishments, dashboard) and `report_service.py` **do not commit** (except `create_report`/`resolve_report`/`dismiss_report`): the route commits once. Every state change calls `record_moderation_action(...)` (table `moderation_actions`) and notifies the affected user. Errors are `ModerationError` subclasses (handled in `app/main.py` like `ReviewError`); `AlreadyAppliedError` (409) means "already in that state" and is ignored when resolving a report.
- Blocking a comment (`comment_status=BLOCKED`) never recalculates ratings; hiding (`status=HIDDEN`) and deleting do. Admin views (`to_admin_review`) always carry the original text; public/panel views go only through `to_public_review`/`to_public_reply`.
- Admin protections: no changing one's own role or suspending oneself, `restaurant` roles are fixed, and never leave the system without an active admin.
- `app/api/routes/catalog_router.py:build_catalog_router(dep, audit=)` serves products, combos, images and schedules for both `/restaurant` (`require_approved_restaurant`) and `/admin/establishments/{id}` (`get_establishment_for_admin`, `audit=True`). The dependency returns `(actor, establishment)`; the audit (`EDIT_CATALOG` + one owner notice per day via `dedupe_key`) is added before the operation, which commits. Add new catalog endpoints there, not in `restaurant.py`.
- Reports (`reports` table, polymorphic target without FK, one per reporter+target) are created by any `require_active_user` account on visible content that isn't theirs; resolving/dismissing closes all open reports on the same target.

### Other integrations

- `app/services/storage.py`: Cloudflare R2 via boto3 presigned upload URLs; returns 503 when R2 credentials are missing.
- Geo (`app/services/establishment_service.py`): latitude/longitude (`Numeric(9,6)`) are the source of truth. `/nearby` prefilters in SQL with `bounding_box` (index `ix_establishments_lat_lng`) and then runs the `haversine_km` `for`/`continue`/`if` loop in Python on that subset; `/map` returns viewport markers ordered by ranking. Listing/nearby use `_LIST_LOAD_OPTIONS` (`raiseload` on reviews) — never return reviews from list endpoints. Location fields are validated by `app/schemas/geo.py` (`Latitude`/`Longitude` round to 6 decimals, `check_coordinates_pair`) and `ensure_in_service_area` (`OutOfServiceAreaError` → 400). Geocoding happens in the frontend; the backend holds no Google Maps key. PostGIS is available but not used yet.
- Ratings (`app/services/rating_service.py`): `establishments.rating_count/rating_sum/rating_avg/ranking_score` are denormalized. Any review change must call `recalculate_establishment_rating(session, establishment_id)` (no commit) before the operation's single commit; `ranking_score` is Bayesian (`RANKING_MIN_REVIEWS`, `RANKING_PRIOR_MEAN`). `scripts/recompute_ratings.py` rebuilds everything. Only `VISIBLE` reviews count (hiding changes the average; blocking a comment does not).
- Reviews (`app/services/review_service.py`): one per user+establishment (`uq_reviews_user_establishment`), only role `user` (active, verified phone) on `APPROVED` places they don't own — `check_can_review` also feeds the detail's `viewer_can_review`/`viewer_review_block`. Domain errors are `ReviewError` subclasses that `app/main.py` turns into `{"detail", ...extra}` (`code` on 403, `review_id` on 409). Convert reviews/replies to output **only** with `to_public_review`/`to_public_reply` (they hide blocked text) or `to_my_review` (author view with the original text). `Establishment.reviews` and `User.reviews` are `lazy="raise"`: no endpoint returns all reviews; use the paginated `GET /reviews/establishments/{id}`. Review image URLs must start with `{R2_PUBLIC_BASE_URL}/reviews/`. The establishment panel (`/restaurant/reviews*`) uses `list_reviews_for_owner`, `reply_stats`, `upsert_reply` (notifies the author once, via `dedupe_key`) and `delete_reply`.
- Schedules (`app/services/schedule_service.py`): local time (`APP_TIMEZONE`), `day_of_week` 0 = Monday; `closing_time < opening_time` crosses midnight. `validate_schedules` (max 3 segments/day, no overlaps across the whole week) guards `PUT /restaurant/schedules`; `is_open_at(schedules, local_dt)` includes the opening and excludes the closing minute — use it to validate plans in B6.
- Plans (`app/services/plan_service.py`, routes `/plans` with `require_planner`: role `user`, active, verified phone): `scheduled_at` must be timezone-aware, is stored in UTC rounded to the minute and validated in local time with `is_open_at` (only if the place has schedules). The total is computed server-side from current catalog prices and frozen per item (`name_snapshot`, `unit_price_snapshot`); never accept a client total. Errors are `PlanError` subclasses (handled in `app/main.py`). `.ics` export in `calendar_service.py` (CRLF, 75-octet folding, escaping, UTC).
- Background cycle (`app/services/reminder_service.py`): `dispatch_due_reminders`, `complete_past_plans` (→ `COMPLETED` + `REVIEW_PROMPT` if the user can still review) and `purge_old_notifications` are idempotent (row state + `dedupe_key`, `FOR UPDATE SKIP LOCKED`), commit themselves and take an explicit `now` (tests call them directly). The `lifespan` runs `app/workers/reminders.py:reminders_loop` when `REMINDERS_ENABLED=true`; `python -m scripts.run_reminders --once` is the cron alternative.

## Tests

Tests use SQLite with `Base.metadata.create_all`, not Postgres. There is no pytest-asyncio. Service-level tests wrap async code in `asyncio.run(...)` (see `tests/test_phone_verification.py`). API tests use the fixtures in `tests/conftest.py`: each test gets a temporary SQLite file (not `:memory:`, which breaks across `TestClient`'s event loop), `get_db` is overridden, and `make_client()` returns a `TestClient` with its own cookie jar (one per actor). `make_client()` behaves like the browser + frontend for CSRF: it sends `Origin: http://localhost:3000` and a response hook copies `csrf_token` from `/auth/*` responses into its `X-CSRF-Token` header, so tests don't handle the token by hand (pop the header or override `Origin` to test rejections). There are also `admin_client`, `user_client(suffix) -> (client, user_id)` (active `user` with verified phone), `register_restaurant(suffix, **overrides)`, `approved_restaurant(suffix, **overrides)` (registered at Cúcuta's center by default), `approved_restaurant_at(suffix, lat, lng, **register_overrides)`, `add_reviews(establishment_id, [ratings])` (one author per review, recalculates aggregates) and `db_session` (an `async_sessionmaker` on the same temp DB: `async with db_session() as session:` inside `asyncio.run`). `conftest.py` sets `REMINDERS_ENABLED=false` before importing the app. Admin/moderation tests share helpers in `tests/moderation_helpers.py` (`post_review`, `notifications`, `actions(db_session, **filters)` to read the moderation log). Tests that need production settings build `Settings(_env_file=None, ...)` or monkeypatch attributes of the `settings` singleton.

Alembic revision ids must be at most 32 characters (`alembic_version.version_num` is VARCHAR(32)).

### Restaurant accounts

`role="restaurant"` users are created by `POST /auth/restaurant/register` together with their `Establishment` (`status` is `PENDING`, `APPROVED`, `REJECTED` — may reapply — or `SUSPENDED` by an admin — may not). They skip OTP verification: their access is gated by the establishment's approval. Routes under `/restaurant` use `require_restaurant_user` or `require_approved_restaurant`, which always resolve the establishment by `owner_id`. Never accept an `establishment_id` from the client there. `require_approved_restaurant` raises `EstablishmentAccessError`, which `app/main.py` turns into a 403 `{"detail", "status"}` response. Products and combos are both `MenuItem` (`is_combo`); a combo's composition is `ComboItem`. The public directory only shows `APPROVED` establishments.
